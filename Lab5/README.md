# FinTrack Simple — лабораторная работа № 5, вариант № 2

Упрощённое учебное Android-приложение для учёта личных финансов. Используются Java 17, XML-разметка, Room, LiveData/ViewModel и WorkManager. Интерфейс состоит из трёх экранов: главная, лимиты и регулярные платежи.

## 1. Что умеет приложение

1. Записывать доходы и расходы, просматривать, редактировать и удалять операции.
2. Считать текущий баланс, доходы и расходы за календарный месяц.
3. Устанавливать один месячный лимит на каждую категорию.
4. Показывать уровень использования лимита и предупреждать о приближении к нему или превышении.
5. Создавать регулярный платёж с ежемесячным напоминанием.
6. Отправлять уведомления через WorkManager. При отказе от разрешения уведомления не показываются, но остальная программа продолжает работать.

Чтобы не усложнять лабораторную, при первом запуске автоматически создаётся один счёт «Основной счёт», а категории доходов и расходов заполняются примерами. Отдельного экрана управления счетами и категориями нет.

## 2. Среда и запуск

- Android Studio Ladybug 2024.2 или новее.
- JDK 17.
- compileSdk 35, minSdk 24, targetSdk 35.
- Gradle 8.13 и Android Gradle Plugin 8.13.2.

Откройте папку `FinTrackSimple` в Android Studio и дождитесь Gradle Sync. Если Android Studio предложит установить Android SDK Platform 35, согласитесь. Затем выберите эмулятор или устройство и нажмите Run.

В архиве нет Gradle Wrapper и готового APK. Если Android Studio не создала wrapper автоматически, можно установить Gradle 8.13 и выполнить в корневой папке проекта:

```bash
gradle wrapper --gradle-version 8.13 --distribution-type bin
./gradlew testDebugUnitTest
./gradlew assembleDebug
```

В Windows вместо `./gradlew` используется `gradlew.bat`.

## 3. Модель базы данных

Созданы шесть таблиц. Четыре из них — основа варианта: `accounts`, `categories`, `transactions`, `category_limits`. Таблица `budget_rules` хранит правила предметной области в виде данных, как рекомендует методичка. Таблица `recurring_payments` хранит расписание платежей, чтобы WorkManager мог восстановить напоминание после закрытия приложения или перезагрузки устройства.

- `accounts`: счёт пользователя. Для минимального сценария создаётся один основной счёт.
- `categories`: категории доходов и расходов. Справочник добавляется автоматически при создании БД.
- `transactions`: сумма, тип, дата, комментарий и ссылки на счёт и категорию.
- `category_limits`: лимит категории для конкретного месяца.
- `budget_rules`: минимальный процент использования лимита, уровень, подпись, цвет и значок предупреждения.
- `recurring_payments`: название платежа, сумма, дата следующего напоминания и признак активности.

Связи и правила удаления:

- `transactions.accountId → accounts.id`, `CASCADE` — удаление счёта удаляет его операции.
- `transactions.categoryId → categories.id`, `RESTRICT` — категорию, которая используется в истории, удалить нельзя.
- `category_limits.categoryId → categories.id`, `CASCADE` — лимиты удаляются вместе с категорией.

Внешние ключи индексированы. Уникальный индекс `categoryId + month` запрещает создать несколько лимитов для одной категории за один месяц. Полная схема: `docs/SCHEMA.md` и `docs/Схема_БД.png`.

## 4. Как работает программа

### Добавление операции

Пользователь выбирает тип (доход или расход), категорию и сумму. Для новой операции автоматически используется основной счёт. После сохранения Repository выполняет запись в Room в фоновом потоке и ставит задачу проверки лимита в WorkManager.

### Расчёт лимита

Суммируются все расходы выбранной категории с начала текущего месяца до начала следующего месяца:

```text
spent = сумма операций категории за месяц
percent = spent * 100 / limit
remaining = limit - spent
```

Дальше `BudgetAnalyzer` получает правила из таблицы `budget_rules` и выбирает правило с наибольшим порогом, который не превышает рассчитанный процент:

| Использование | Уровень | Цвет |
|---|---|---|
| Меньше 80% | Норма | зелёный |
| 80–99% | Приближение к лимиту | оранжевый |
| 100–119% | Лимит превышен | красный |
| 120% и больше | Существенное превышение | тёмно-красный |

### Уведомление о лимите

После записи операции создаётся одноразовая задача WorkManager. Через небольшую задержку `FinanceWorker` заново читает актуальные сведения из БД, вызывает `BudgetAnalyzer` и показывает уведомление, если серьёзность состояния выросла. Повторное уведомление того же уровня не отправляется.

### Напоминание о регулярном платеже

Пользователь указывает название, сумму и дату первого напоминания. `ReminderScheduler` создаёт `OneTimeWorkRequest` с задержкой до этой даты. `FinanceWorker` показывает уведомление, сдвигает дату на следующий месяц и планирует новую задачу. Удаление платежа отменяет все связанные задачи по тегу.

## 5. Основные понятия

- **Room** — библиотека Android поверх SQLite. Описывает таблицы классами и проверяет SQL-запросы при сборке.
- **Entity** — класс, который соответствует таблице БД.
- **Primary key** — уникальный идентификатор строки.
- **Foreign key** — внешний ключ, связывающий запись с другой таблицей.
- **CASCADE** — удалить зависимые записи вместе с родительской.
- **RESTRICT** — запретить удаление родительской записи, если на неё ссылаются.
- **Index** — структура для ускорения поиска и соединения таблиц.
- **DAO** — интерфейс SQL-операций с базой.
- **@Relation / @Embedded** — способ получить сущность вместе со связанными записями.
- **Repository** — посредник между ViewModel и БД; запись выполняется через `ExecutorService` в фоновом потоке.
- **ViewModel** — хранит данные экрана и готовит рассчитанные состояния бюджета.
- **LiveData** — сообщает экрану об изменениях наблюдаемых данных.
- **WorkManager** — надёжно планирует отложенные фоновые задачи, в том числе после перезапуска устройства.
- **NotificationChannel** — канал уведомлений Android, где пользователь может настроить важность сообщений.
- **POST_NOTIFICATIONS** — разрешение, которое приложение запрашивает на Android 13+.

Суммы хранятся в целых копейках (`long`), а не в `double`, чтобы избежать ошибок округления.

## 6. Проверка

1. Запустить приложение. Список операций должен быть пустым, баланс — нулевым.
2. Добавить расход 850 ₽ в категорию «Продукты».
3. На экране «Лимиты» установить для «Продукты» лимит 1 000 ₽. Должно появиться предупреждение о приближении к лимиту (85%).
4. Добавить ещё 150 ₽ расходов в эту категорию — статус должен стать «Лимит превышен».
5. Нажать на операцию, изменить или удалить её. Суммы и статус лимита должны пересчитаться.
6. Создать ежемесячный платёж. Для быстрой проверки выберите сегодняшнюю дату: после 09:00 задача должна выполниться практически сразу.
7. Удалить платёж и убедиться, что его будущие задачи отменены.
8. На Android 13+ отказать приложению в разрешении на уведомления. Добавление операций и работа с лимитами должны остаться доступными.
9. Перезагрузить устройство и проверить, что будущая задача WorkManager сохраняется.

Пояснительная записка с ответами на вопросы раздела 8 находится в `docs/Пояснительная_записка.docx`. Подробное объяснение понятий и алгоритмов — `docs/Объяснение_понятий_и_алгоритмов.docx`.

В проект включён один обязательный unit-тест: проверка перехода в состояние «Приближение к лимиту» при расходе 85% от лимита.

## 7. Что намеренно не реализовано

Не выполняются бонусные задания: расширенный набор тестов, действия непосредственно из уведомления и дополнительная визуализация бюджета. Также не добавлены отдельные экраны управления счетами и категориями, несколько счетов и недельная периодичность платежей — это не требуется для демонстрации основных сценариев варианта.
