# Памятка к защите: «Книга рецептов»

## Краткая демонстрация (2–3 минуты)

1. Открыть приложение и показать пустое состояние каталога.
2. Добавить рецепт: заполнить название, категорию, время, ингредиенты и шаги; выбрать фотографию или сделать снимок камерой. Пока фото обрабатывается, появляется индикатор.
3. Показать карточку, переключить каталог со списка на сетку, закрыть приложение/вернуться и убедиться, что выбор вида сохранён.
4. Открыть карточку целиком: показать экран деталей и полноэкранное фото. Развести два пальца, приблизить изображение и переместить его.
5. Отредактировать рецепт, затем показать подтверждение удаления. Удаление убирает и фото из внутреннего каталога.
6. Запланировать готовку на дату и время. Показать разовое и еженедельное повторение. При совпадении с занятым временем появляется предупреждение; после подтверждения событие и напоминание создаются в календаре.
7. Для проверки устойчивости отказать в доступе к календарю и показать, что каталог продолжает работать.

## Основные участки кода

### `RecipeDbHelper.java`
SQLiteOpenHelper создаёт локальную таблицу `recipes`. Строка хранит текстовые поля и путь `image_path`, а также `calendar_event_id`, дату и флаг еженедельного повторения. Путь к изображению — обычная строка, а не Uri галереи. `getAllRecipes()` возвращает данные для списка, `insertRecipe()`/`updateRecipe()` сохраняют форму, `deleteRecipe()` удаляет запись.

### `RecipeAdapter.java`
`RecyclerView.Adapter` вручную создавать заново не нужно: `ListAdapter` работает с `DiffUtil.ItemCallback`. `areItemsTheSame()` сравнивает постоянные ID записей; `areContentsTheSame()` сравнивает содержимое. `ViewHolder` ищет `ImageView` и `TextView` один раз при создании держателя. В `onBindViewHolder()` устанавливаются заголовок и метаданные, а Glide асинхронно загружает файл по пути с ограничением размера. Обработчик установлен на `itemView`, поэтому нажимается вся карточка.

### `ImageUtils.java` и `RecipeFormActivity.java`
Сначала `inJustDecodeBounds=true` читает ширину/высоту без декодирования пикселей. Затем `calculateInSampleSize()` выбирает степень двойки для предварительного уменьшения. После декодирования возможное превышение размеров устраняется точным масштабированием до 1024 пикселей по длинной стороне. `Bitmap.compress(JPEG, 80, ...)` уменьшает размер файла. Файловая обработка запускается в `ExecutorService`, поэтому не блокирует главный поток UI. После успешного сохранения в SQLite попадает абсолютный путь файла из `files/images`.

Галерея подключена контрактом `PickVisualMedia`, камера — `TakePicture` и `FileProvider`. Эти варианты дают приложению временный доступ к выбранному/снятому фото, после чего оно создаёт собственную сжатую копию. Разрешение на чтение всей галереи не нужно.

### `ZoomImageView.java`
`ScaleGestureDetector` отслеживает жест двух пальцев. `Matrix` задаёт масштаб и перемещение изображения. Начальный масштаб подбирается так, чтобы изображение помещалось в экран; предел увеличения — пятикратный относительно исходного экранного масштаба. При перемещении применяется ограничение, не позволяющее полностью увести изображение за границы видимой области.

### `CalendarHelper.java` и `RecipeDetailActivity.java`
Перед работой проверяются `READ_CALENDAR` и `WRITE_CALENDAR`. Метод `findWritableCalendarId()` выбирает календарь, в котором уровень доступа не ниже `CAL_ACCESS_CONTRIBUTOR`. Для поиска занятости используется `CalendarContract.Instances`, потому что этот контракт возвращает экземпляры повторяющихся событий в заданном диапазоне. При пересечении выводится подтверждение.

Событие создаётся через `ContentResolver.insert(CalendarContract.Events.CONTENT_URI, values)`. Для повторяющегося события задаются `DURATION` и `RRULE=FREQ=WEEKLY;INTERVAL=1`; для разового — `DTEND`. Часовой пояс задаётся через `EVENT_TIMEZONE`. После вставки берётся ID из Uri результата, создаётся напоминание через `CalendarContract.Reminders`, а ID события сохраняется в SQLite. Благодаря ID событие можно найти и удалить при удалении рецепта.

### `MainActivity.java`
В зависимости от сохранённого значения SharedPreferences RecyclerView получает `GridLayoutManager(2)` или `LinearLayoutManager`. Empty state показывается при нулевом числе записей. Позиция прокрутки обычно сохраняется при возврате с экрана деталей, поскольку MainActivity остаётся в стеке и RecyclerView не пересоздаётся.

## Вопросы по пояснительной записке (раздел 8 задания)

**1. Почему копируем фото во внутреннее хранилище, а не сохраняем Uri?** Доступ по Uri, выданному системным Photo Picker, может быть временным. Собственная копия в `Context.getFilesDir()` доступна приложению после перезапуска устройства, а в БД хранится стабильный путь. Другие приложения не получают прямой доступ к файлу.

**2. Какие параметры компрессии выбраны?** Длинная сторона — максимум 1024 px, JPEG quality — 80. Размер достаточен для карточки и просмотра на экране телефона, а качество 80 обычно даёт разумный компромисс между детализацией и размером файла. Средний размер надо измерить на реальных тестовых снимках: он зависит от содержимого и не является постоянным.

**3. Почему два этапа декодирования?** Полноразмерный снимок может распаковаться в десятки мегабайт. Сначала считываются только размеры, затем `inSampleSize` уменьшает количество декодируемых пикселей. Это снижает пиковое потребление памяти до последующего масштабирования.

**4. Как организованы потоки?** Сжатие, декодирование и запись идут в `ExecutorService`. Результат возвращается в UI через `runOnUiThread()`. Главный поток остаётся доступным для касаний и обновления интерфейса.

**5. Что происходит при удалении рецепта?** Приложение удаляет запись SQLite и файл по сохранённому пути. Если удалять только строку, фотографии останутся бесхозными и со временем займут место во внутреннем каталоге.

**6. Почему календарь записывается напрямую?** `CalendarContract` позволяет создавать событие и напоминание без перехода в стороннее приложение, сохранять ID и позднее удалять связанное событие. Цена — разрешения READ/WRITE_CALENDAR и необходимость учитывать отказ пользователя, недоступность календаря и уровень прав.

**7. Какое правило повторения используется?** Для повторяющихся блюд `FREQ=WEEKLY;INTERVAL=1` — раз в неделю. Одна серия проще для редактирования и не заполняет календарь большим количеством отдельных событий.

**8. Зачем хранить ID календарного события?** ID связывает строку рецепта с записью календаря. Без него нельзя надёжно найти, изменить или удалить именно созданное приложением событие.

**9. Что если пользователь отказал в разрешении?** Функция планирования отключается, показывается понятное сообщение. Работа с каталогом, фотографиями и рецептами не блокируется.

## Термины, которые нужно понимать

- **RecyclerView** — контейнер, который переиспользует видимые элементы при прокрутке.
- **Adapter** — соединяет данные модели с визуальной карточкой.
- **ViewHolder** — хранит ссылки на View внутри элемента, чтобы не вызывать `findViewById()` при каждой привязке.
- **LayoutManager** — определяет геометрию списка/сетки.
- **DiffUtil** — сравнивает старый и новый список и обновляет только различия.
- **Glide** — библиотека асинхронной загрузки, масштабирования и кэширования картинок.
- **Uri** — идентификатор ресурса; он не равен постоянному пути собственного файла.
- **Bitmap** — декодированные пиксели изображения в памяти.
- **RRULE** — строка правил повторения из стандарта iCalendar.
- **ContentResolver** — интерфейс доступа к данным Android-провайдеров, в данном случае к календарю.
- **SharedPreferences** — небольшое локальное key-value хранилище настроек, здесь используется для выбранного вида каталога.
